# Data model, provenance, and history

This service stores source-backed university data independently from the Andromeda core database. Every imported record belongs to one `data_releases` row and has a stable `external_key`; internal UUIDs stay inside PostgreSQL and are not part of the API contract.

## Evidence and typed links

`source_artifacts` records the downloaded page or document, including the source URL, fetch time, SHA-256, storage state, and local content path when available. `source_evidence` points to one artifact and records the field path, source locator, optional excerpt or claim, source observation time, and verification state.

Evidence-to-entity relationships use dedicated tables such as `program_evidence`, `offering_evidence`, and `curriculum_evidence`. Those tables have composite foreign keys over both `release_id` and the target row. PostgreSQL therefore rejects evidence that points to a missing target or crosses release boundaries. The bridge table also prevents a polymorphic string from being the only integrity check.

Admission offers, competition pools, requirement sets, and statistics also retain the exact source direction or department code where the source provides one. If that code has no confirmed canonical catalog row, its typed foreign key stays `NULL` and the source code remains queryable; no name-based join is performed. Source observations and manual-review rows retain the fuller original context.

## Time on factual assertions

For mutable admission facts, the service stores assertions as versioned rows. The temporal columns have separate meanings:

| Column | Meaning |
| --- | --- |
| `valid_from`, `valid_to` | The source-stated period when the assertion applies. Either may be `NULL` when the source does not give that boundary. |
| `observed_at` | When the source was observed, only when the bundle provides that timestamp. |
| `ingested_at` | When the service stored the row, generated by PostgreSQL. |

`NULL` means unknown or unstated. The importer must not fill source-valid or source-observed time with the download or import time. Conflicting source rows remain separate assertions and can be linked to manual review. Once a release is committed, database triggers reject inserts, updates, and deletes for its admission requirement sets, place/quota assertions, competition pools, tuition, achievement policies, and admission statistics. A correction is loaded as a new release.

## Requirements and decision policy

`admission_requirement_sets` and ordered `admission_requirement_nodes` preserve source requirements as boolean trees. `AND`, `OR`, and `AT_LEAST` retain their original operators and thresholds. These rows describe admission requirements and are not policy packs used by an eligibility decision engine.

Decision policies, when introduced separately, use `rule_packs`, typed `rule_scopes`, and `rule_pack_versions`. A `NULL` scope axis is a wildcard. PostgreSQL 16 enforces one exact axis tuple even when some axes are `NULL`, and a GiST exclusion constraint prevents overlapping published date ranges for the same scope. Drafts may overlap. The resolver selects the most specific active match and returns a stable ambiguity error when equally specific wildcard scopes tie.

The BMSTU 2026 export does not provide decision policy packs, so the initial import must leave these tables empty. Admission requirement trees are stored in their dedicated tables instead.

## Migration safety

Migrations are owned by `services/academic-data/migrations/` and use the service-local Alembic version table. Downgrade of the temporal/evidence migration is refused while releases, import batches, or policy versions exist. For populated installations, back up and migrate forward; do not edit committed facts in place.
