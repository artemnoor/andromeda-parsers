# Тематическая классификация предметов

## Назначение

Классификация добавляет к каталожным курсам и строкам учебных планов отдельный версионируемый слой смысловых фактов. Исходные записи не переписываются, а их названия не используются как идентификаторы. Связь идёт по внешнему ключу конкретной записи и по текущему выпуску данных.

Для каждой записи Jev отдельно выбирает ровно одну из 16 категорий. Пакетирование нескольких независимых вопросов в один API-запрос служит только для экономии сетевых обращений: ответ и проверка остаются отдельными для каждой строки. Совпадающие названия классифицируются повторно с контекстом своего направления, кафедры и профиля; результат одной строки на другую не переносится.

## Происхождение и воспроизводимость

Выгрузка результата содержит:

- стабильные внешние ключи предметов;
- хеш конкретного входа, хеш исходной выгрузки и хеш активного выпуска;
- выбранный Jev код, полный ответ, вероятности для всех категорий и уверенность;
- провайдера, запрошенную и разрешённую версии модели;
- версию и SHA-256 инструкции классификатора;
- время/стоимость и итоговый статус запуска в manifest.

После импорта те же ключевые поля сохраняются в отдельном запуске и отдельных фактах классификации. У факта есть настоящий внешний ключ либо на `catalog_courses`, либо на `curriculum_items`; оба варианта одновременно запрещены ограничением БД. Категория ссылается на конкретную версию справочника. Выпуск данных, запуск классификатора и его результаты неизменяемы: новая таксономия, инструкция или выпуск создают новую версию фактов, а не затирают старую.

Фактическая подтверждённая стоимость хранится отдельно от любых неучтённых запросов. Если старый запуск не сохранил usage конкретного ответа, manifest фиксирует число таких ответов и пояснение, но не выдумывает их цену.

Таблицы: `subject_taxonomies`, `subject_taxonomy_categories`, `subject_classification_runs`, `subject_classifications`. UUID применяются только как внутренние ID в PostgreSQL. Перед загрузкой резолвер сверяет внешние ключи и названия со всем активным выпуском и отказывает при неполном покрытии или расхождении источника.

## Категории

Коды `01`–`16` соответствуют списку заказчика и являются стабильными внутри `bmstu-subject-domain-16:v1`. Описания границ категорий уточняют задачу модели и не добавляют утверждений о конкретных курсах. Изменение названий/границ требует новой версии таксономии или промпта.

1. Математическая база
2. Физика и естественно-научная база
3. Информатика, программирование и Computer Science
4. Данные, ИИ и вычислительное моделирование
5. Информационные системы, сети и архитектура ИТ
6. Информационная безопасность
7. Автоматика, управление, робототехника и мехатроника
8. Конструирование, проектирование и CAD/CAE
9. Механика, прочность и инженерный расчёт
10. Материалы и производственные технологии
11. Отраслевые инженерные специализации
12. Дизайн и визуальные дисциплины
13. Экономика, менеджмент, логистика и предпринимательство
14. Гуманитарные, коммуникационные и языковые дисциплины
15. Право, безопасность труда и нормативка
16. Практики, НИР и итоговая аттестация

## Контроль качества

Автоматическое распределение локальными правилами, ключевыми словами или копированием ответа для одинаковых названий запрещено. Локальный код валидирует допустимый код категории, полноту всех 16 вероятностей, сумму вероятностей, уверенность и точное совпадение сохранённого ответа Jev с выбранным кодом.

Причины `needs_review` являются только сигналом для ручной проверки и не меняют выбор модели:

- уверенность ниже `0.70`;
- разница между двумя максимальными вероятностями меньше `0.10`;
- Jev выбрал код, вероятность которого ниже вероятности другого кода;
- после завершения прогона одинаковое название в пределах одного типа источника получило разные ответы.

Требования к загрузчику: принимать только завершённый прогон с одним разрешённым выпуском Jev, совпадающими хешами и полным взаимно-однозначным покрытием входных внешних ключей. Частичный результат хранится в checkpoint-файле и не выдаётся за опубликованный полный прогон.

## Повторный запуск

Из `services/academic-data`, не запуская парсеры:

```powershell
$env:PYTHONPATH = "src"
uv run python -m academic_data_service.classification.jev `
  --bundle ..\..\backend\exports\andromeda_bmstu_2026_bundle `
  --output artifacts\bmstu-2026\subject-taxonomy-16\jev-results.jsonl `
  --release-digest <активный-хеш-выпуска> `
  --batch-size 16 --timeout 90 --retries 5
```

Ключ хранится в `POLZA_AI_API_KEY` и не записывается в результат. Если API временно недоступен или отвечает HTTP 402, выполнение прекращается, manifest помечается как незавершённый, уже проверенные ответы остаются в JSONL. После восстановления доступа команда продолжает с checkpoint и не отправляет завершённые строки повторно. Загрузчик PostgreSQL намеренно отклоняет такой неполный прогон.

Импортировать можно только после того, как manifest имеет `status=complete`, `completed_records=expected_records`, число результатов совпадает с числом исходных строк и `failed_records=0`:

```powershell
uv run python -m academic_data_service.classification.importer `
  --bundle ..\..\backend\exports\andromeda_bmstu_2026_bundle `
  --results artifacts\bmstu-2026\subject-taxonomy-16\jev-results.jsonl `
  --manifest artifacts\bmstu-2026\subject-taxonomy-16\jev-results.manifest.json
```

Доступность API/импорт и выгрузка незавершённого прогона — разные статусы: checkpoint не считается данными опубликованной версии.

Проверить полное или частичное покрытие и сформировать CSV ручной проверки можно без вызова модели:

```powershell
uv run python tools/report_subject_classification.py `
  --bundle ..\..\backend\exports\andromeda_bmstu_2026_bundle `
  --results artifacts\bmstu-2026\subject-taxonomy-16\jev-results.jsonl `
  --manifest artifacts\bmstu-2026\subject-taxonomy-16\jev-results.manifest.json `
  --report artifacts\bmstu-2026\subject-taxonomy-16\qa-report.json `
  --review-csv artifacts\bmstu-2026\subject-taxonomy-16\manual-review.csv
```
